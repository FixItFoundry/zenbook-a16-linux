## 2. Root-cause chain (definitive, per project's own logs)

1. **Old wall (pre-pKVM):** Retail firmware's XBL Dynamic-Init grants the MDSS xPU only to the Hypervisor-HLOS VMID (`acvmid = 0x3C`). Bare-metal EL2 VHE Linux presents VMID 0 → `VBIF+0x160` write → xPU deny → silent warm-reset. (DISPLAY-BRINGUP-FINDINGS.md, G17.)
2. **Wall bypassed (pKVM):** `kvm-arm.mode=protected` runs the host under a stage-2 with a nonzero VMID. The bare-host `VBIF+0x160 ← 0x22222223` write **lands, permitted, no reset**, and reaches the panel (G18; 07_DTB_CHANGELOG test48). → **No Gunyah, no CMA needed.**
3. **New blocker (UNDER BARE-METAL EL2, pre-pKVM):** msm binds DPU, reads panel EDID (Samsung ATNA60HR07, 2880×1800@60/120, 10bpc), backlight found — then **eDP link training times out (`-110`)** and/or warm-resets at first modeset.
4. **The catch-22 (pre-pKVM theory):** `simplefb` (UEFI continuous splash) is the only active consumer of the MDSS GDSC. Power-cycling MDSS → XPU grant wiped → crash. **UNVERIFIED under pKVM** — the VMID grant may make this moot. The surviving pKVM boot log never exercised msm, so this is hypothesis, not observed fact.

## 3. Assessment of the msm_gem CMA rewrite

**Files:** `msm_gem_rewrite.c` (1587 lines), `msm_gem_rewrite.h`, `msm_gem-rewrite.md`.

**Verdict: ABANDONED (user-confirmed).** Reasons:
- Premise ("host can't write SMMU registers / needs CMA to bypass SMMU") is moot on glymur — the VMID wall is cleared by pKVM, and SMMU StreamID `0x1de0/0x1de1` was already verified correct vs firmware; buffers map fine at commit.
- The `-110` is a **DP PHY / link-training** failure, orthogonal to GEM buffer allocation.
- The rewrite as supplied is **incomplete**: `msm_gem_get_phys_addr()` is exported but **no caller feeds it to `SSPP_SRC_ADDR`** — the §3.4 DPU changes in the .md were never written into the .c/.h. Even on its own terms it wouldn't route display through CMA.
- The .md still says "Snapdragon X Elite" and describes `iommu_attach_device()` hypervisor traps — that's the x1e pKVM issue, a carry-over from a different SoC.

**Note:** CMA may still be a *future* optimization for contiguity once a real modeset works, but it is not the display fix.

- eDP `displayport-controller@af6c000` → **`status = "okay"`** (line 3369) with `aux-bus { panel { compatible = "samsung,atna60cl08","samsung,atna33xc20"; enable-gpios = <0x69 0x12>; } }` (lines 3398–3411). `0x12` = **gpio18**.
- `gpio-reserved-ranges` (line 4047) = `<2 1> <4 4> <10 10> <22 14> <49 2> <52 15> <68 2> <71 5> <149 3> <155 94>`:
  - `<10 10>` = pins **10–19 reserved → pin 18 is STILL LOCKED**. msm, if un-blacklisted, would fail to request the eDP enable-gpio → probe defer, no modeset.
- **Surviving boot log `dmesg.log` is a CLEAN pKVM boot** of this exact entry: reaches `systemd` (line 1031). Only faults are the **chronic ghost-SPMI WARNs** (`pmic_arb_wait_for_done ... transaction failed (0x3)`, sids 0x7/0xb — known cosmetic noise, doc'd in changelog). **There is NO crash in the log.**
- **Correction to prior session:** the claim "test57 crashed chasing eDP" is UNSUBSTANTIATED. With msm blacklisted, msm never ran, so no VBIF/`-110` fault could occur. The `-110`/catch-22 narrative belongs to the pre-pKVM test48/test51 era and has NOT been re-observed under pKVM.

**Implication:** To actually test whether pKVM's VMID grant lets msm modeset, we need test58 = test57 + pins 18 & 70 freed + msm **un-blacklisted**. That boot has never been done.

**CRITICAL REGRESSION (confirmed 2026-07-14 + 2026-07-15, empirical):** `test57.dtb` with **msm LOADED** (mdss `okay`) **BLOWS AWAY WIFI** — garbled console, black screen, boot chime, no net/SSH. `dt-pkvm` (test57 + msm *blacklisted*) boots clean WITH wifi (proven by `dmesg.log`). So: mdss-enabled DTB + msm loaded = wifi dies; mdss-enabled + msm blacklisted = fine. Root cause unconfirmed (runtime MDSS↔PCIe/wifi PD/NoC/SMMU coupling, NOT a DT-node diff — `pci@1c00000` + `vreg_pmu_*` identical to test55-usb). **Daily driver remains `test55-usb.dtb` (mdss disabled, wifi works, simplefb only).** Any mdss-enabled+msm-loaded boot is diagnostic-only; never repoint the default grub entry to it. See §6/07_DTB_CHANGELOG "test57 WiFi regression".

## 5. Implementation plan (no msm_gem rewrite)

All work on the **`dt-pkvm` entry + `kvm-arm.mode=protected`**. pKVM already supplies the VMID → no Gunyah, no CMA.

### Phase 0 — Reconcile docs + baseline (read-only / low-risk)
- **P0.1:** Write `DISPLAY-CURRENT-STATE.md`: VMID wall = BYPASSED via pKVM; remaining blocker = eDP `-110` under MDSS-power catch-22; msm_gem CMA rewrite = abandoned. Stops future AI plans re-fighting the old war.
- **P0.2:** Confirm on-box what `dt-pkvm` boots (which DTB, is `mdss` enabled, is pin 18 freed). **BLOCKER for execution.** If it = test55-usb (mdss disabled), the display work hasn't started on that entry.

### Phase 1 — Build the real display-attack DTB (test57 derivative)
- **P1.1:** From `test57.dts`, create `test58-display.dts`: **free pin 18** by splitting `<10 10>` → `<10 8> <19 1>` (mirror test47/test48). Free pin 70 too if its regulator EN needs it (currently `<68 2>` keeps 68-69 reserved, 70 is already free between 69 and 71).
- **P1.2:** Keep `simplefb` active (do NOT pass `video=simplefb:off`).
- **P1.3:** Boot with msm **UN-blacklisted** under pKVM (`dt-pkvm` minus `modprobe.blacklist=msm`). This is the first boot that actually exercises the VBIF write under a nonzero VMID. Capture `dmesg` + `drm.debug=0x1f6`.
- **P1.4 (safe first step):** Boot test58 with msm STILL blacklisted to confirm the DTB delta (pin free) doesn't regress the clean boot, then un-blacklist on the next boot.

### Phase 2 — Observe what actually happens under pKVM (the real goal)
- **P2.1:** The prior `-110`/catch-22 was under bare-metal EL2. With pKVM's VMID grant, the VBIF write that caused the warm-reset may now succeed → the `-110` may not reproduce at all. Let the log tell us, don't assume the old failure.
- **P2.2:** If msm binds and reaches link training: identify failing stage (AUX EDID, clock recovery, channel eq) from `drm.debug`. If msm binds and produces a framebuffer → display is WORKING under pKVM; the wall is fully bypassed.
- **P2.3 (if it still resets at modeset):** then the catch-22 is real and we apply the in-place same-resolution (2880×1800) handoff to avoid the MDSS power-cycle. But this is now a SECONDARY hypothesis, not the assumed blocker.

### Phase 3 — External DP proof (isolation)
- If Phase 2 stalls: boot with internal eDP disabled (test49 approach) to confirm a real modeset on external DP lights up under pKVM — proves DPU scanout end-to-end works, isolates issue to eDP PHY/panel.

### Explicitly OUT OF SCOPE (per user): msm_gem CMA rewrite (abandoned), Gunyah (pKVM won), IORT/SDEV ACPI diff (`gpu_smmu_routing_from_WoA_ACPI.md` missing from folder; it's Adreno GPU routing, not eDP-relevant).
