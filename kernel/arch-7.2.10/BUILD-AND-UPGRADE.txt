Arch Linux ARM 7.2.10 A16 development packages

The checked-in source/config replay builds an independent development kernel.
It does not replace the shared linux-omarchy package or establish hardware
acceptance. Source identity, upstream recipe revision and the 127-patch queue
remain pinned in build.json; packaging changes do not change that source tree.

Build on an Arch Linux ARM aarch64 host/container:

  python3 prepare-package.py /new/package-output --pkgrel 3
  cd /new/package-output
  makepkg

The default rebuild revision is 3. Use a new positive --pkgrel for a new build;
never publish different kernel contents under an already installed revision.
Revision 2 belonged to the legacy fixed-name package, so the new default starts
at revision 3 to avoid colliding with that installed module tree.
Source archives and the reproducible backport bundle have mandatory SHA-256
checks. The build validates its release, required configuration and A16 DTB.
makepkg captures compiler/dependency information in .BUILDINFO.

Each build emits four packages, for example:

  linux-omarchy-a16-7.2.10-3
  linux-omarchy-a16-7.2.10-3-headers
  linux-omarchy-a16-tracking
  linux-omarchy-a16-tracking-headers

The tracking packages depend on that exact payload/header revision. Upgrading
them leaves prior versioned payloads installed: module trees, headers, DTBs,
metadata, presets and UKI names differ for each revision. Keep the old payloads
installed until the new kernel passes physical acceptance. Explicit package
removal or orphan cleanup can still remove an old rollback kernel. Existing
legacy linux-omarchy-a16 packages are neither replaced nor removed.

The payload contains /usr/lib/modules/RELEASE/zenbook-a16-boot.json with actual
kernel/DTB/config hashes and the verified source tree. Its policy name is
omarchy-a16-legacy-v1: this identifies the existing standalone startup profile,
not shared Omarchy DSP ABI 1 and not successful hardware testing. No ABI marker
or ABI-providing dependency is fabricated. The current omarchy-a16-support
package depends on the shared linux-omarchy ABI/header contract; standalone
packages do not satisfy those dependencies. Reuse the shared Omarchy package
and its existing support setup for the production Arch path.

Standalone UKI builds are explicit and require mkinitcpio plus systemd-ukify.
Each payload installs its own mkinitcpio preset and /usr/lib/modules/RELEASE/uki.conf pointing at its matching DTB:

  sudo mkinitcpio -p linux-omarchy-a16-7.2.10-3
  sudo /usr/lib/omarchy-a16/verify-boot --bootloader limine \
    --kernel-release 7.2.10-omarchy-a16-3

The preset follows Limine's machine-ID/custom-name prefix and writes a distinct
UKI. It does not change the configured boot default. Check root/cmdline and
signed ASUS DSP firmware, and arrange the existing standalone startup profile
before building. The private uki.conf does not inherit global signing or PCR
settings: configure signing explicitly there before use on a secured system.
The explicit verifier requires matching headers and validates metadata plus
the UKI's release/kernel/DTB/initramfs; its default shared-kernel selection is
unchanged. Install the updated support verifier or run the checked-in verifier
with Python when checking this development package.

Automatic standalone Limine updates remain unsupported. The current external
Limine hook bypasses mkinitcpio presets and reads one global uki.conf; Omarchy's
hardware setup chooses a global DTB directory. It cannot reliably select a
different versioned DTB for each installed kernel. Do not reboot after a generic
UKI regeneration without rebuilding and checking the intended standalone UKI.
This repository does not silently patch the shared kernel's boot integration.

Keep the working kernel, its headers/modules/DTB/UKI and an independent bootable
installer. The a16_dsp=off recovery profile is the same kernel with DSP startup
disabled; it does not replace a previous-version rollback. USB-root safety,
four-speaker playback, microphone, audio after idle, battery/charging and Wi-Fi
need physical acceptance. Package-generation tests do not establish these.
Vendor-signed firmware and card-specific Wi-Fi calibration remain separate.
